# v5c の API 費用 — 実測の内訳と「1/10」に届くかの試算

作成 2026-08-28（CTO）。**報告のみ。この文書ではシミュ本体・台本・分類器に一切手を入れていない。**

数値の出所は 3本の実ラン（`simulations/2026-08-28_1016_100_field_v5c_runA` /
`_1110_100_field_v5c_runB` / `_1110_100_field_v5c_runC`）の `summary.json` にある
`usage.by_tag`（API が実際に返したトークン数）と、`configs/config_field_v5c.yaml` の
`cost.price_table` だけ。手打ちの数字は無い。再現：

```
python tools/cost_breakdown_v5c.py
```

単価（`gemini-2.5-flash-lite`・config の price_table）：
入力 $0.10 / 100万トークン、**キャッシュ読み $0.01**（入力の1/10）、出力 $0.40 / 100万トークン。

- **runB** calls 4,969／入力 11,448,770（同 2,271,392＝19.8%）／出力 1,742,528 → **$1.6375**（1か月 $0.0682）
- **runC** calls 4,771／入力 10,727,182（同 2,227,882＝20.8%）／出力 1,642,679 → **$1.5293**（1か月 $0.0637）
- **3本合計 $4.8907**

1シーンあたり（1か月＝計画1巡＋シーン4本×2巡）：runC で **$0.0637 ÷ 4シーン ≒ $0.016**。

**費用の内訳は入力57%・出力43%**（runC：入力 $0.872／出力 $0.657）。
出力が4割を占めるのは、全コールが JSON 構造化出力（内心＋発話＋メモ）で、
分類器が1コールあたり 1,098 トークンも書き戻しているため。

## 4. 「入力のうち毎回同じ前置き」の割合

- 住民の固定前置き（`build_system_prompt_v5c` が作る system prompt）は**実測 1,639 文字**。
  役割説明・街の背景・自分のペルソナ・出力形式の4ブロックで、**月やシーンで変わらない**。
- 実際に**キャッシュ単価で課金された入力は全体の 18.4〜20.8%**（1コールあたり平均 467 トークン）。
- 一方、月初シーン（S1r1）の入力は1コール 1,358 トークンしかない。
  **前置きはこの大半を占めているはずなのに、キャッシュに載っているのは 37.1% どまり**
  ＝明示キャッシュが効いている枠と効いていない枠がある。分類器は 0%。
- **要確認**：文字→トークンの換算比はモデル依存で本便では未計測（Gemini の
  `count_tokens` を1回叩けば確定できる。API を叩くので施主承認の対象）。
  上の 1,639 文字が何トークンかは確定していない。ここは推定を書かない。

結論：**「毎回同じ前置き」は月初のコールでは入力の過半だが、後半のシーンでは1〜2割まで下がる。**
キャッシュを完全に効かせても、入力費用が消えるわけではない（後述の試算）。

## 5. 「1/10」に届くか（runC の $1.5293 を基準にした試算）

施主採用の3案（①Batch API 50%オフ ②共通前置きのキャッシュ最大化 ③出力の短縮）を、
上の実測トークンに掛けた試算。**実装は本便では行っていない。**

- **現状**　$1.5293（基準の100%）
- **A案（安全側）**：分類器のみ Batch＋キャッシュ35%＋出力-25% → **$1.0812（71%・1/1.4）**
- **B案（攻め）**：全コール Batch＋キャッシュ55%＋出力-50% → **$0.4867（32%・1/3.1）**
- 参考：B案＋1シーンの同席を8人上限（コール-35%） → $0.3163（21%・1/4.8）
- 参考：さらに月内2巡→1巡 → $0.2214（14%・1/6.9）

**採用済みの①〜③だけでは 1/10 に届かない。届くのは 1/3（B案）まで。**
理由は単純で、①は最大50%オフ、②が効くのは入力のうち前置き分だけ、③は出力（費用の43%）の
半分まで、と上限が決まっているから。1/10 に行くには**コール数そのものを減らす**しかなく、
それは「誰が誰と同席するか」「何巡話すか」＝世界の条件を変えることになる。

### 各案の判定（創発を歪めないか）

1. **Batch API（50%オフ）** — 歪めない（同じプロンプト・同じ順序で投げるだけ）。ただし
   **実務上の壁**：ラウンドは同期の壁（前の巡の発話が次の巡の入力）なので、
   24か月×(4シーン×2巡＋計画)＝216回のバッチ投入が直列になる。Batch には返却時刻の保証が無く、
   1本のランが数時間〜数日になりうる。**確実に効くのは事後の分類器（775コール・費用の31%）**で、
   ここは1回のバッチにまとめられる。→ **分類器のBatch化は無条件で推奨、ループ内のBatch化は
   所要時間と引き換え。**
2. **共通前置きのキャッシュ最大化** — 歪めない（プロンプトの中身は1文字も変えない）。
   いま 20.8% しか載っていないので、明示キャッシュのTTL・作成失敗のログ確認・
   前置きが最小トークン数に届いているかの確認で伸びしろがある。**最優先で安全な案。**
3. **出力の短縮** — **条件付きで歪める**。`max_tokens` の上限を下げるだけなら打切り
   （runC の max_token_finishes は 6 本）が増えて発話が途中で切れる＝観測が壊れる。
   一方、**分類器の出力**（1コール1,098トークン）は理由文を短くしても街の挙動には触れない
   ＝**安全**。内心（thought）の長さを縛るのは、内心が発話の材料である以上
   **街の語りを変えうる＝要注意**。→ 分類器の出力短縮は可、主体の出力短縮は慎重に。
4. **1シーンの同席者を6〜8人に絞る**（現状 attend_slots 1,935＝1シーン約20人が15会場に分散）
   — **歪める。** 誰が誰と居合わせるかは、この研究が測っている当のもの。実験条件の変更であって
   節約策ではない。やるなら別条件のランとして立てる。
5. **分類器をルール先行にして LLM は候補行のみ** — **歪めない**（事後の測り方であって世界ではない）。
   ただし現在の判定（ルール1次抽出 ∧ LLM）は**すでにルール先行**であり、
   LLM に渡っているのは絞ったあとの行。さらに絞ると偽陰性（人手監査で実測 8.0%）が増える。
   **測定精度と引き換え。**
6. **月内2巡→1巡／記憶の要約圧縮** — **歪める。** 2巡目は「他人の発言を聞いてから返す」場で、
   火が点く経路そのもの。記憶の圧縮も、何を覚えているかを変える＝観測条件の変更。
7. **モデル据え置き** — 施主指示どおり据え置き前提で試算した。

### 施主判断用のまとめ

- **A案（安全側・創発に一切触れない）＝ 1/1.4。** 中身：分類器のBatch化＋キャッシュを効かせる＋
  分類器の出力短縮。世界の条件は1つも変わらない。
- **B案（攻め）＝ 1/3。** A案＋ループ内もBatch化（＝1本のランに数時間〜数日かかるのを許容）＋
  主体側の出力も短縮（打切りが増えないか要検証）。
- **1/10 は、同席人数・巡数・記憶のどれかを削らないと届かない**＝
  「狙った動きを出す仕組みは入れない」の裏返しで、**観測条件そのものを削ることになる。**
  費用を1/10にしたいなら、**ランの本数か月数を減らす**（3本→1本、24か月→12か月）ほうが
  研究として正直。3本24か月で $4.89。本数・月数はそのまま費用に効く（月数を半分にすれば、
  会話の記憶が短くなる分だけ比例より安くなる＝実測は取っていないので数字は書かない）。
