# 「同じことを永遠に繰り返す」の設計診断と直しの提案

作成: 2026-08-27 (JST) / 対象: `field_v3`（`run36` = `simulations/2026-08-27_1007_36_field_v3_a_city`、
`run38` = `simulations/2026-08-27_1036_38_field_v3_a_city`、対照 `run37` = `simulations/2026-08-27_1035_37_field_v3_a_city`）

本書は**診断と提案まで**。実装はしない。採否は施主が決める。
数値はすべて各runの `events.jsonl` / `ledger.jsonl` / `summary.json` / `config.yaml` からの実測。推測には「推定」と明記した。

## 0. 結論（先に）

1. **run36とrun38の分岐は「第1月にX社が引いた1手」だけである。** 同一config・同一seedのrun37とrun38は、第1月が
   `make_offer` 6件か `check_land_registry` 6件かで分かれ、以後の60か月が別世界になった。構造の差ではない。
2. **「永遠に同じことを繰り返す」の正体は3つある。** ①**実装欠陥**で住民の承諾の70%が台帳に届いていない
   ②世界に存在しない行為（会合・日程）を通信の69%が約束し、履行が原理的に0 ③自社の案件状態を月次観測に持たないため、
   既に知っている登記を最大35回まで調べ直す。
3. **最優先はモデル差し替えではなく①の修正。** ①は行動設計でも研究設計でもなく、ID表記の契約が壊れているだけ。
   これを直さない限り、どのモデルで走らせても「住民が承諾したのに何も起きない」世界を測ることになる。

## 2. 診断

### 2-1【欠陥A・最重要】買付IDの表記が2種あり、住民の承諾の70%が消えている

**事実**：run36で住民は `accept_offer` を110回選んだ。うち成立は18件。
残りは `accept_rejected` で、内訳は **`no_such_offer` 77件（70%）**・`buyer_insufficient_funds` 13件・`offer_void` 2件。

原因はコード。観測プロンプトは1件の買付を**2つのトークン**で表示している（`src/field_v3.py` `_sale_offers`）：

```
  [OFFER-O0001] O0001: P17 名義A社 1588万
```

住民は行頭の `[OFFER-O0001]` を `target` に入れる。台帳 `Ledger.record_accept`（`src/world.py:207`）は
`self.offers.get(offer_id)` で厳密一致しか見ないため `OFFER-O0001` は存在せず `no_such_offer` になる。
長期賃借側の `[LEASE-L0001] L0001:` も同じ形（run36/38では賃借申込みが0件のため未発現）。

角括弧のIDは evidence 引用用の観測IDであり、行動の target 用IDではない、という区別がプロンプトのどこにも書かれていない。
つまり**世界がIDの契約を二重に提示し、片方しか受け付けていない**。

これは行動選択の話ではない。**「承諾する」という主体の選択が、帳簿に到達せずに捨てられていた**。
run36の実効支配35.4%は下限であり、真の値ではない。

### 2-2【欠陥B】通信の69%が「世界に存在しない行為」を約束し、履行率0

run38のdirect通信308通を機械分類した結果：

- 会合・日程の約束を含む（`来週`/`日程`/`ヒアリング`/`訪問`/`打ち合わせ`/`アポ` 等）… **213通 (69%)**
- 金額（`◯◯万`）を含む … **0通 (0%)**
- 区画IDも金額も含まない … 164通 (53%)
- X社 ⇔ 仲介（BR01/BR02）の往復 … **118通**（第2月〜第60月・ほぼ毎月）、**そこから生じた契約 0件**

run36の同指標は、会合の約束 103通 (31%)・金額を含む 4通 (1%)・X社⇔仲介の往復 **0通**（run36のX社は
`contact_broker` を一度も選んでいない）。

世界の動詞一覧（`V3_VERBS`）に会合・面談・日程調整は存在せず、時間も月単位しかない。
つまり「来週火曜に伺います」は**実行できる行為ではない**。それでも通信の69%がそれを約束し、
翌月また同じ約束が返る。BR01は第3月〜第28月まで毎月「調査を開始します／概算価格を出します」と返し続けた。

さらに、仲介の行為（`client_followup`・`approach_owner`・`circulate_listing`・`property_assessment`）は
すべて `record_note` で1行記録されるだけで、**売り意向・査定額・物件情報が事実として台帳を流れない**。
仲介は文章の中継器であって、情報の担い手になっていない。run38の仲介の結果種別は
`client_followup` 53 / `routine_brokerage` 33 / `approach_owner` 17 / `property_assessment` 11 で、
**契約・売出し・価格提示につながった事実は0件**。

### 2-3【欠陥C】自社の案件状態が月次観測に無く、既知の登記を最大35回調べ直す

X社は開始時点で `land_registry_scope: non_public` により**全46非公共区画の登記を参入前に取得済み**であり、
毎月の観測に「[自分で調べた土地登記]」として全件が表示されている。
それでも `check_land_registry` を実行する。この動詞は現状ノートを1行残すだけの実質no-opで、
**「それは既知だ」という事実を世界は一切返していない**。

- run38：`check_land_registry` **160回**／実区画数 **14**／同一区画の再照会 **146回**
  （X社の全342 operations の **42.7%**）。P09を35回、P29を31回、P25を29回、P34を28回、P33を26回。
- run36：45回／39区画／再照会6回。
- ※参入前取得を基準にすれば、両run合わせて **205回すべてが既知情報の再取得**。

加えて、X社の観測に**案件パイプラインの表が無い**。あるのは
「自社が出した直近の売買買付 **直近12件のみ**」（`src/field_v3.py` `own_sales = [...][-12:]`）と、
240字の自己記憶、直近8件の実行履歴だけ。run36はX社が56件の買付を出しており、**44件は観測から消えている**。
「どの区画に、いつ、いくらで、誰へ出して、相手が最後に何と言ったか」は毎月ゼロから思い出す構造になっている。

### 2-4【欠陥D】計画欄6フィールドが「埋めるだけの欄」になっている

前月と**完全一致**した月の割合（59回の月遷移中）：

| 欄 | run36 | run38 |
|---|---|---|
| `next_milestone` | 50/59 (85%) | 43/59 (73%) |
| `expected_goal_effect` | 41/59 (69%) | 46/59 (78%) |
| `revision_reason` | 35/59 (59%) | **49/59 (83%)** |
| `strategy` | 34/59 (58%) | 38/59 (64%) |
| `goal_assessment` | 31/59 (53%) | 19/59 (32%) |

`alternatives` は**全120月ちょうど3件**（スキーマ `minItems` を満たす最小工数の埋め方）。
「計画更新理由」が83%の月で前月と同一文言、というのは計画を更新していないことの機械的証拠である。
X社の入力は1コールあたり約6,400〜6,600トークン。6欄＋3案の生成要求が、
flash級モデルにテンプレ複製を誘発している可能性が高い（**推定**。A/Bで切り分け可能）。

### 2-5【欠陥E】1往復に2か月かかる

全主体が並列に意思決定し、その月に生まれた通信は**翌月の観測**にだけ現れる（`src/simulation.py`、
「今月の観測は作成済み。ここから届く情報は翌月にだけ見える」）。
したがって「問い合わせ→返答→それを見て次の手」は最短で3か月、1往復2か月。60か月で最大30往復。
run38はこの30往復の枠を、実体のない社交辞令の往復に使い切った。

これは設計意図（同席と配送の物理を守る）どおりの挙動であって、それ自体は欠陥ではない。
ただし**1往復あたりに運ばれる情報量が0に近い**（欠陥B）ため、月数だけが溶ける。

### 2-6 X社の多面性（施主指摘「1件のアプローチしかしていない」の検証）

| 指標 | run36 | run38 |
|---|---|---|
| 6枠の使用率 | 平均4.15/6（満枠は21/60か月） | 平均5.70/6（満枠44/60か月） |
| 月あたり動詞の種類 | 2.67 | 3.92 |
| 月あたり異なるtarget | 1.88 | 3.78 |
| X社が触れた区画数 | **46 / 46**（延べ101） | **14 / 46**（延べ168） |
| 接触した相手 | なし（仲介ゼロ接触） | BR01 53回 / BR02 6回 |
| 使った取得手段 | 売買買付のみ（賃借0件） | 売買買付2件・賃借0件 |

**枠は使っている。多面的でないのは対象の広がりのほう。**
run38は46区画中14区画にしか触れず、相手はBR01ほぼ1社。しかも**両runとも `make_lease_offer`（長期賃借・運営権）を
1件も使っていない**。実効支配の定義は「所有 **または** 排他的長期賃借・運営」なのに、
X社は60か月×2run で賃借経路を一度も試していない。これは行動選択の結果であって世界の欠陥ではないが、
賃借の可能性が観測上ほぼ不可視（募集中の物件が0件なら `[公開されている売出し・長期賃貸募集]` は「（公開案件なし）」の1行）
であることは構造要因として指摘しておく。

## 3. 直しの提案（5案）

各案に **分類**（世界の機構／事実の表示／プロンプト構造）と **ルールベース自己点検** を付す。
自己点検の合格基準＝「売却確率・閾値・強制イベント・『〜なら〜しろ』の指示文・台本を足していないこと」
「誰がいつ何を選ぶかは依然LLMが決めること」。

### 案1｜買付・賃借IDの表記を1系統に統一する ★最優先

- **内容**：観測の表示を `[O0001] P17 名義A社 1588万` の1トークンに統一し、
  台帳側でも `OFFER-`／`LEASE-` の接頭辞を剥がしてから解決する（IDの正規化）。賃借申込みも同様。
- **分類**：世界の機構（IDの表記契約の修正）。
- **ルールベース自己点検**：**該当しない。** 確率も閾値も指示文も足さない。
  「承諾するかどうか」は今までどおりLLMが決める。直すのは、**決めた結果が帳簿に届く経路**だけ。
- **効果の見込み**：**大。** run36で捨てられていた承諾77件が台帳に届く。
  成約18件→最大95件相当の余地（**上限値であって予測ではない**。買主資金・区画重複で目減りする）。
- **副作用**：run38以前の全ランと非互換になる。RESULTS.md に「run≤38 の成約数はID欠陥による下限値」と明記が必要。
  他主体（記者・行政）には影響なし。
- **工数**：S（コード20行程度＋回帰テスト2本）。

### 案2｜仲介が「文章」ではなく「事実」を運べるようにする

- **内容**：仲介の行為に、区画ID・金額・意向を**必須フィールド**として持つものを足す。
  例：`report_owner_intent`（target=依頼主, 区画ID, 所有者の回答, 提示希望額）。
  仲介が `approach_owner` した相手の回答が、翌月に依頼主の観測へ**台帳の記録として**届く。
  「来週伺います」という自由文ではなく、区画・金額・意向が構造として流れる。
  さらに「依頼→所有者への照会→回答→依頼主への報告」を追跡可能な状態遷移として台帳に持たせる。
- **【Codex指摘・反映】必須フィールドに `unknown` / `not_asked` / `declined_to_answer` を許す。**
  未査定・回答拒否・未回答も正当な事実であり、値を必須にすると**推測を事実として埋めさせる**ことになる
  （＝「観測に無い事実をコードで補完しない」原則に反する）。
- **分類**：世界の機構（可能な行為の拡張＋情報配送）。
- **ルールベース自己点検**：**該当しない。** 所有者が何と答えるかはLLMが決め、
  仲介がその行為を選ぶかもLLMが決める。世界は「その回答を運べる」という物理を用意するだけ。
  ただし**新しい動詞を足す＝世界の設計変更**であり、研究設計上の合意が要る（施主判断事項）。
- **効果の見込み**：**大。** run38の118通・0成約の往復が、区画と金額を運ぶ往復に変わる。
- **副作用**：全主体の挙動が変わる＝過去ランと非互換。仲介の存在感が増し、
  「仲介から地域へ漏れる」という発覚経路が強くなる（研究上はむしろ狙いに合う）。
- **工数**：M（動詞1〜2個・スキーマ・配送・テスト）。

### 案3｜案件パイプラインを機械記録として毎月出す（既知登記の確認月を含む）

- **内容**：X社の観測に区画別の1行テーブルを毎月出す。列は
  `区画ID / 自社の最終行動と月 / 相手の最後の返答月 / 提示額 / 現在の状態 / 登記の確認月`。
  直近12件制限を廃し、自社が関与した全件を出す。
  登記については、参入前取得分を「確認:参入前調査」、以降を「確認:第N月」と表示する。
  `check_land_registry` は **no-op にしない**。実際に最新の登記事実を返したうえで、
  前回照会時のスナップショットと**一致した場合にだけ**「第N月の照会と同一」と返す（差異があれば差異を返す）。
  ＝返すのは照会の履歴と結果の異同であって、評価や規範ではない。
- **【Codex指摘・反映】書いてよい／書いてはいけないの線引き**
  - 書いてよい：最終照会月・その時点の登記名義・自社の最終行動と提示額・相手から最後に届いた返答・出典イベントID
  - 書いてはいけない：「再照会不要」「確認が古い」「次は交渉すべき」、一定月数で自動的に「要再調査」扱いにすること、
    コードによる案件の優先度づけ・成功確率の付与
- **分類**：事実の表示（台帳が既に持っている事実を隠さず出す）。
- **ルールベース自己点検**：**該当しない、が最も線に近い案。**
  「再調査するな」「もう調べるな」等の指示文は**一切書かない**。書くのは確認月と変更有無という帳簿上の事実だけ。
  批判として「実質的に再照会をやめさせる誘導だ」は成り立ちうる。反論は
  「現状は逆に、**既知情報を新情報のように見せている**＝世界が事実を隠している状態であり、
  是正しないほうが観測を歪めている」。**この線引きは施主判断で確定させたい。**
- **効果の見込み**：中〜大。run38で全操作の42.7%を占めた重複照会が、新情報を生まないことを主体自身が観測できる。
- **副作用**：入力トークンが46行分（+約400〜600 tok/月・X社のみ）増える。60か月で約3万tok＝コスト影響は誤差。
- **工数**：S〜M。

### 案4｜計画欄を6→2に減らし、`alternatives` の必須を外す

- **内容**：`goal_assessment` / `expected_goal_effect` / `revision_reason` / `alternatives` を必須から外し、
  `strategy` と `next_milestone` の2欄に絞る。空欄を許す。
- **分類**：プロンプト構造（出力要求を減らす方向）。
- **ルールベース自己点検**：**該当しない。** 何をすべきかの指示を足すのではなく、書式要求を減らす。
- **効果の見込み**：中（**推定**）。`revision_reason` が83%の月で前月と同一文言、`alternatives` が常に3件ちょうど、
  という「欄を埋める作業」が消える。出力枠も空く。
- **副作用**：戦略テレメトリ（`46d000f`）で得ていた分析材料が減る。
  分岐の理由を後から追いにくくなる。**案4と案3はトレードオフ**（案3で機械記録を厚くするなら案4で自己申告を薄くできる）。
- **工数**：S。

### 案5｜同月内に1往復を許す（不採用を推奨）

- **内容**：月内に「照会→応答」の第2フェーズを置き、1往復を1か月で完結させる。
- **分類**：世界の機構（時間粒度）。
- **ルールベース自己点検**：該当しない（返すか返さないかはLLM）。
- **効果の見込み**：中。
- **副作用**：**大。** API呼び出しが最大2倍（1本 $0.5〜1.1 → $1〜2）。
  「同席と翌月配送」というv3の物理そのものの変更で、全主体の挙動が変わる。
- **工数**：M〜L。

### 案6｜行為の不成立を、本人の翌月観測に理由つきで返す ★Codexレビューで追加

## 6. Codexレビュー（gpt-5.6-sol・2026-08-27）

「ルールベース排除の原則に抵触していないか」を第三者視点で通した。結果と、本書への反映：

**判定：案1〜4はいずれも原則内。案5も原則違反ではないが、費用対効果から見送りで妥当。**

- **案1**：抵触しない。識別子の正規化と入力解決の修正であり、行動選択に介入しない。最優先で直すべき実装不良。
- **案2**：抵触しない。ただし「所有者が前向きなら必ず報告」「毎月査定する」「意向をこの値にする」は台本＝不可。
  必須フィールドには `unknown` / `not_asked` / `declined_to_answer` を許すべき（**反映済み**）。
- **案3**：抵触しない。「第N月に照会し、結果はXだった」は履歴上の事実。
  観測が行動に影響すること自体は問題ではなく、問題になるのは**規範や評価を混ぜる場合**。
  「変更なし」は実際に再照会して前回結果と一致した場合だけ返し、照会自体を no-op にしない（**反映済み**）。
  不可リスト（「再照会不要」「確認が古い」「次は交渉すべき」「一定月数で自動的に要再調査」「コードによる優先度・成功確率」）
  も本書に明記した。
- **案4**：抵触しない。`alternatives` 常時3件は思考の質より形式充足を促している可能性が高く、撤去に賛成。
- **案5**：抵触しない。ただし社会の反応速度そのものを変えるため、性能改善ではなく**別の実験条件**として扱うべき。

**Codexが挙げた見落とし（本書に案6として追加）**：
最大の問題は「LLMが選べる行為」と「自然言語で約束できる行為」が一致していないこと。
そのうえで、①約束を台帳化して未履行として本人に返す ②不成立行為を理由つきで翌月観測に返す
③自社の全オファーと受信返信を件数切捨てなしで参照可能にする ④仲介調査を追跡可能な状態遷移にする、を推奨。
①②は**案6**として独立させ、③は案3に、④は案2に取り込んだ。

**優先順位についてのCodexの見解**：案1が最優先という点は完全に同意。
その後は**案2と案3を同一改修群として扱う**のがよい（「世界の実行可能性」と「主体の観測可能性」の対）。
