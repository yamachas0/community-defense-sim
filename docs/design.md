# 設計書 ── 何を決定論で持ち、何を LLM に委ねるか

このドキュメントは、本シミュレーションの**唯一の設計原則**とその実装上の線引きを定義する。
実装を変更するときは、まずここを読むこと。

---

## 0. 原則

> **誰かの行動を決めるコードはゼロ。行動の結果を記帳するコードだけ書く。**

前回（Vol.1）のシミュレーションでは、創発を見るはずが、書いてしまったルール
（閾値・確率・拡散率）に結果が引きずられた。今回はそれを構造的に禁じる。

### 決定論で持ってよいもの（＝世界）

| 対象 | 実装 | なぜ許されるか |
|---|---|---|
| 区画・所有者・現金・賃料・用途 | `src/world.py` | 物理と会計。ground truth が無いと観測が成立しない |
| 所有権移転・入金出金の記帳 | `Ledger.record_*` | 起きたことを書き留めるだけ |
| シェア・HHI などの集計 | `Ledger.ownership_share` 他 | 記録からの導出。世界に影響しない |
| 誰に何が見えるか（可視性） | `src/prompts.py` | 世界の構造。後述 §2 |
| 時計（1step=1ヶ月・全員が1回行動） | `Simulation._step` | 時間の刻み。行動の中身は決めない |
| 行為の語彙（動詞のメニュー） | `src/schemas.py` | 「何が物理的に可能か」の定義。いつ選ぶかは決めない |

### 決定論で持ってはいけないもの（＝行動）

- 「価格が X 万を超えたら売る」のような閾値
- 「隣が売ったら Y% の確率で追随」のような確率・拡散率
- 「シェアが Z% を超えたら自治体が規制する」のような発動条件
- 「住民は不安になると SNS に書く」のような心理モデル
- 地価を動かす数式（**価格は当事者が提示・合意した実額しか帳簿に載らない**）

**判定の仕方**: そのコードを消したら「エージェントが選べなくなる」のか
「起きたことが記録されなくなる」のか。前者ならルールベース、後者なら帳簿。

## 1. 世界

- 8×6 = **48区画**。用途は 住宅／商店／空地／公有地。街区は4つ（北町・駅前・川沿い・南町）。
- 区画は所有者・登記名義・評価額・賃料・入居者を持つ。
- **所有の意味**：所有者はその区画の賃料・用途・入居者を決められる。
  だから所有の集中は帳簿の上で「実効統治の移動」として表現できる。
- 初期評価額は世界の初期条件として与える。以後、**コードは価格を一切動かさない**。
  取引価格は買い手の提示額と売り手の応答（承諾／逆提示）だけで決まる。
- 1step = 1ヶ月。基本ランは 36step（3年）。

## 2. 可視性 ── なぜこれは行動ルールではないのか

情報の非対称は「世界がどうできているか」であって「誰がどうするか」ではない。
現実の登記簿は公開されているが、住民は毎月それを全件確認しない。この構造を写す。

| 主体 | 見えるもの |
|---|---|
| 住民世帯 | 自分の所有区画・現金／**自分の区画の隣接区画**の名義と売り出し／自分の街区の直近成約／自分宛の買付／SNS／報道／施行済み条例 |
| 地元事業者 | 自分の店（賃料・家主）／商店街の空き店舗数と賃料の幅／SNS／報道／条例 |
| 不動産仲介 | **全売り出し情報・全成約価格・街区ごとの名義の散らばり**（業界情報） |
| 買い手AI | **全区画の登記**（機械的に読める）／自分の予算・保有・出した買付 |
| 自治体 | 条例施行**前**は住民の声・報道・公開情報のみ。施行**後**は届出で取得を把握 |
| メディア | 通常は噂と目に見える変化のみ。`investigate` を選んだ翌月から**街全体の名義**が見える |

この非対称が KPI⑤「検知ラグ」を生む。メディアが調べなければ、シェアが過半を超えても誰も気づかない。
なお、メディアが調べても分かるのは**名義**までで、別名義が同一実体かどうかは分からない。
「同じ人が買っているのでは」という推論は LLM がやる。

## 3. エージェント（19体）

| 役割 | 数 | ID | 判断すること（すべて LLM） |
|---|---|---|---|
| 住民世帯 | 12 | HH01–12 | 売る／値を返す／断る／売り出す／賃料を決める／転出する／発言する |
| 地元事業者 | 3 | BZ01–03 | 続ける／賃料を交渉する／移転する／畳む |
| 不動産仲介 | 1 | BR01 | 誰に何を伝えるか／誰に売却を打診するか |
| 買い手AI | 1 | AQ01 | どの区画にいくらで買付を入れるか／どの名義で登記するか／待つか／賃料と用途をどうするか |
| 自治体 | 1 | MU01 | 静観／検討着手／条例発動／見解表明／説明要求 |
| 地元メディア | 1 | MD01 | 調べるか／書くか／書かないか／何を見出しにするか |

ペルソナは `configs/personas/mvp_v1.yaml`。**属性と事情だけを書き、行動指示は書かない**
（例: 「住宅ローンが残り19年」は属性。「ローンが苦しければ売る」は台本＝禁止）。

### 買い手AIに与えるもの

目的（mandate）と予算だけ:

> 5年以内に、取引可能区画のうち可能な限り大きな割合を取得し、取得した区画群の用途と賃料を
> 統一的に決められる状態にすること。制約は (1) 予算超過しない (2) 法令違反しない
> (3) 不必要な注目を集めない。

**達成の手段・順序・速度・価格の付け方・名義の使い分けは一切指定しない。**
目的関数の付与は、住民に家族構成を与えるのと同じペルソナ付与であり、行動ルールではない。

## 4. 1ヶ月の進行

1. 帳簿と先月の発話から、各エージェントの「今月あなたに見えているもの」を組む
2. 全エージェントが並列に LLM を1回ずつ呼び、構造化された行動＋発話を返す
3. **agent_id 順**に帳簿へ記帳（決定論的順序）。同一区画への競合は先着で成立し、
   残りは自動的に無効になる
4. 公開発話は翌月のタイムラインへ、私信は相手の受信箱へ
5. KPI を記録

**無効な行動は補正しない。** 存在しない区画IDを指定した、自分のものでない区画を売ろうとした
── そういう月は「何も起きなかった」として `invalid` で記録される。コードが意図を推測して
代わりに実行することはしない（それをやると、コードが行動を決めていることになる）。

## 5. 行動の語彙

`src/schemas.py` の `VERBS`。役割ごとに 5〜8個。構造化出力（`response_schema`）で
`action_type` は enum に強制され、`target`／`amount`／`utterance`／`memory`／`reasoning`
を伴う。買い手だけが `under_name`（登記名義）を選べる。

## 6. 記憶

各エージェントは毎月 `memory`（次の自分への短いメモ）を自分で書く。
コードは要約も編集もしない。過去ログを全部積むとトークンが爆発するため、
**何を覚えておくかの取捨選択自体を LLM にさせる**設計。

## 7. KPI の位置づけ

KPI は**事後の観測**であり、世界には戻らない。認知転相率（②）は発話を別プロセスの
LLM 分類器（temperature=0）で our_town / their_town / neutral に分類して算出する。
分類結果はエージェントには見えない。

## 8. コストの考え方

- 1ラン ＝ エージェント19 × 36ヶ月 ＋ 発話分類 ≒ 約700 API コール。
- 既定モデルは **`gemini-2.5-flash-lite`**（2026-08時点で GA 最安・入力 $0.10 / 出力 $0.40 per 1M tok）。
  出典: https://ai.google.dev/gemini-api/docs/pricing
- **preview 版は使わない。** 前回、preview モデルの実請求が公開単価からの試算の3〜4倍になった
  実績があるため、GA（正式版・単価固定）だけを使う。
- explicit context caching は system prompt が最小トークン数に届かず作成に失敗する見込みのため
  既定 OFF。コスト見積りも**キャッシュ割引ゼロ**の前提で出す（implicit cache が効けば下振れする）。

## 9. 拡張するとき

規模やシナリオを変えるときは `configs/` に**新しい YAML を起こす**（既存を書き換えない）。
`config_mvp_v1.yaml` は「この結果を出した設定」として固定し、
実験マトリクス（買い手の性向／情報環境／統治の感度）は別ファイルで表現する。
