## 2. それでも世界側に足りていない物理（＝設計不備）

### 不備A（実装漏れ・修正済み `9a7c968`）

依頼主が書いた文面を、仲介の行に表示していなかった（所有者側には表示していた）。
台帳が持っている事実の配送漏れなので直した。

### 不備B（要判断）｜仲介に報酬の物理が無い

`Ledger.settle_month` が動かす金は「事業者の粗利」と「店舗賃料」だけで、
**仲介手数料の記帳はどこにも存在しない**。仲介がどれだけ働いても帳簿は動かない。
これは行動の動機づけ（＝ルール）の話ではなく、**契約と会計の物理が世界に無い**という話である。

**案B**：成約時に、その案件を運んだ仲介へ手数料を記帳する。

- 対象：`transfer`（売買成立）と `lease_control`（長期賃借・運営成立）。
- 「運んだ仲介」の定義は台帳で追跡できるものだけ：**その区画の照会（`Q`）で `reported` に達している仲介**。
  該当がなければ手数料は発生しない（仲介を通していない取引はそのまま）。
- 率は世界の契約条件として `config` に1つだけ置く（例 `world.brokerage_fee_rate: 0.03`）。
  取引額（売買は価格、賃借は月額賃料×一定月数）に率を掛けた額を、買主・売主のどちらが払うかも
  config の契約条件として固定する。**確率でも閾値でもなく、単価表と同じ「世界の初期条件」**。
- 仲介の観測には `[今月の手数料収入] 第N月 P05 売買 手数料NNN万（出典 O0007）` という**事実行**だけを出す。
  「だから照会しろ」とは書かない。

**論点**：手数料という報酬が存在すると、仲介の行動が変わりうる。これは「動機を注入した」のではなく
「現実の仲介業に存在する会計を世界に入れた」と読むべきか、施主の判断が要る。

### 不備C（要判断）｜仲介の処理能力が構造的に足りない

X社は月6件の実務を並行できる（`acquirer_monthly_operation_capacity: 6`）が、
**仲介は月1行動**しか取れない。runA では依頼232件に対し、仲介2社の総行動枠は60か月で120。
依頼を全部受けても物理的に処理しきれない。

**案C**：`world.broker_monthly_operation_capacity`（既定は 1 のまま）を config に持ち、
1より大きいときは仲介も X社と同じ `operations[]` スキーマで複数件を並行実行できるようにする。

- 機構は既存の acquirer 用経路（`action_schema_v3` の operations 分岐と
  `_process_acquirer_portfolio`）をロール非依存に一般化するだけ。新しい規則は足さない。
- 枠を「使う／使わない」は今までどおり仲介が決める。枠超過は既存どおり `monthly_capacity_exceeded`。

**論点**：枠を増やすことは能力の前提を変える世界設計の変更なので、比較したい条件（1件 vs 3件）を
施主が決める必要がある。

## 3. 実装順の推奨

1. 不備A（済）。
2. 施主が案B・案Cの採否を決める。**両方入れると、どちらが効いたか分からなくなる**ので、
   入れるなら1つずつ（B→計測→C、または C→計測→B）を推奨する。
3. 入れた後は同一設定3本で分布を測り直す（1本 ≈ $0.72）。

## 4. この文書で扱っていないこと

- 「依頼が来たら照会する」等の台本は書かない（大方針）。
- 一定月数で自動的に何かが起きる仕掛けも置かない。
- X社が `make_offer` を4本とも1件も選ばなかったこと（買付より照会を選び続けた）は、
  上記2案とは独立の観測であり、別途 `RESULTS.md` に記録した。
