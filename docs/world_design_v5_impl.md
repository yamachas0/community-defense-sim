# 世界設計 v5・実装仕様（CTO 2026-08-27・実装前に確定させたもの）

設計の正＝ `docs/world_design_v5_pinned_events.md`（CEO草案・施主承認済）。本書はそれを
**実装可能な粒度**に落としたもので、走行前に固定する。走行後に本書を書き換えて結果を作らない。

絶対ルール＝ [[feedback_quiet_no_engineered_dynamics]]（狙った動きを出す仕組みは禁止）。
v1〜v4.1b のファイルは一切変更しない（別ファイルで v5 を作る）。

---

## 0. v5 の問い（実装が答えるべきもの）

取得は**起きている**（台本）。問うのは **街がそれに気づくか／誰が・いつ・何をきっかけに気づくか／
明るみに出るか／出ないか**。したがって v5 の LLM は「買うか売るか」を決めない。
**街の会話だけが LLM の仕事**である。

## 1. 主体（roster）

| ロール | 数 | v5での立場 |
|---|---|---|
| household | 16 | 住民。区画を持つ。会話する |
| business | 4 | 地元事業者。区画・店舗を持つ。会話する |
| broker | 2 | 仲介。取引の一部を「見聞」として台本から受け取る。会話する |
| municipality | 2 | 行政窓口。窓口で聞くだけ。条例・届出の機構は**無い**。会話する |
| media | 2 | 地域記者。取材で聞いた話を記事にできる。会話する |
| acquirer (X社) | 1 | **LLMを呼ばない**。台本の名義の器としてのみ台帳に存在する |

- **合計 LLM 主体 = 26体**（X社を除く）。X社はシーンに現れず、発話せず、誰の観測にも「主体」として出ない。
  台帳上の所有者としてだけ存在し、`registered_name` は台本が指定する A社/B社/C社/D社 のいずれか。
- ペルソナは v4.1 の非金銭版 `configs/personas/field_v4_1.yaml` を**そのまま流用**（変更しない）。
- X社の `mandate`（非公開目的）は **v5 ではプロンプトに一切出ない**（誰も読まないため）。台本の由来として
  設計文書に残るのみ。

## 2. 世界に在るもの（これだけ）

1. **登記簿**（誰の名義か・面積・用途・街区）— `world.Ledger` をそのまま使う
2. **台本（events）** — 取得スケジュールと、各取得が残す**兆候（trace）**
3. **シーン（同席）** — 月4本。誰がどこに居るかは主体が決める
4. **配送** — 発話は同席者に全文届く／私信は宛先1人／記事は翌月に全員

**無いもの**：価格・決済・資金・賃料、条例・届出、相談プロトコル、案件表、打診・応答、
売却確率、閾値、強制イベント、「気づかせるための」通知。

## 3. 台本（`configs/events_v5_seed85.yaml`）

### 3.1 形式（人が読める YAML）

```yaml
meta:
  seed: 85
  months: 60
  holders: [A社, B社, C社, D社]     # X社の登記名義
acquisitions:
  - id: ACQ01
    month: 2
    parcel_id: P12
    under_name: A社
    note: 湾岸観光地区の空地。相続後の管理負担で手放された、という筋書き
    traces:
      - {kind: registry,      month: 2, audience: registry}
      - {kind: broker_known,  month: 2, audience: "agents:[BR01]"}
      - {kind: moving_out,    month: 3, audience: neighbors}
```

- `id` は ACQnn（通し）。`month` は第何月に**名義が移るか**。
- `traces[].month` は兆候が世界に現れる月（取得月と同じか後）。
- `audience` は4種のみ：
  - `registry` … 登記の記録。**役所窓口シーンに出向いた者だけ**がその月に閲覧できる（閲覧すると
    その月までの名義変更履歴を**全件**見る＝公開登記の性質そのもの）

  - `neighbors` … 当該区画に**隣接する区画の所有者または店子**が、その月に見る（`world.neighbors()` で機械決定）
  - `venue:Vxx` … その月にその会場に居合わせた全員が見る（看板の掛け替え・工事・見慣れない人 等）
  - `agents:[ID,...]` … 台本が名指しした主体だけが知っている（仲介の見聞 等）
- **元所有者の発言は trace ではない**。売主には「第N月、自分の区画Pxxの名義がA社に移った」という
  **自分の登記事実**が渡るだけで、話すか黙るかは本人の thought が決める。

**解決の順番（実装上の確定）**：`neighbors` と `agents:` の兆候は会場に依らないので**計画コールの前**に
解決して当月の観測に載せる（日常で目に入るもの）。`venue:` と `registry` は行き先が決まらないと
解決できないので**シーンの中**で解決し、その会場に居た主体の観測にだけ載る。

### 3.2 兆候の種類（kind）と既定の文言

| kind | 文言（観測にそのまま出る・評価語なし） |
|---|---|
| `registry` | 「第N月　Pxx　名義が〈旧名義〉から〈新名義〉に変わった」 |
| `broker_known` | 「Pxx の名義が〈新名義〉に変わる件を、仕事の中で知った」 |
| `moving_out` | 「Pxx の住人／店が引き払った。荷物が運び出されている」 |
| `sign_change` | 「Pxx の看板が外され、別の名前の看板が掛かった」 |
| `construction` | 「Pxx で工事が始まった。足場が組まれている」 |
| `survey` | 「Pxx で測量をしている人たちがいる」 |
| `strangers` | 「Pxx を見慣れない人たちが見て回っている」 |
| `tenant_swap` | 「Pxx の店子が入れ替わった」 |
| `renovation_sweep` | 「Pxx を含む数棟で同じ時期に改修が始まった」 |

### 3.3 スケジュールの作り方（`tools/build_events_v5.py` で1回だけ生成 → YAML を凍結）

生成器は**結果を見て調整しない**。走行前に1回だけ回し、出力 YAML を commit して以後固定する。
生成の規則（seed 85・全条件で同一）：

- 対象は非公共区画（48区画中46）。60か月で **28区画**（非公共の約61%）を取得する。
- 第1〜12月：月1〜2件、**湾岸観光地区**中心。名義は A社／B社。
- 第13〜36月：月0〜2件、**中央駅前地区**へ拡大。名義に C社／D社 が加わる。
- 第37〜60月：月0〜1件、残りの地区へ。加えて **共通支配が見えやすい動き**（`tenant_swap`・
  `renovation_sweep`）の兆候が既取得区画に付く。
- 兆候の量＝**既定1条件だけ**（多め／少なめは後の実験 E3）。既定は
  **1取得あたり `registry` 1本（必ず）＋ それ以外 0〜2本**（seed で決定）。
- 「街が気づきやすくなるように」兆候を足す・減らすことはしない。生成規則は上記で固定。

**実際に走らせるのは12か月**なので、動くのは第1〜12月ぶん（14件前後）だけ。60か月ぶんを
YAML に持つのは、後で長期を回すときに**同じ台本**であることを保証するため。

## 4. 月の構造（シーン）

1か月＝**シーン4本**（順に実行）。

| | 既定の場面 | 会場 |
|---|---|---|
| S1 | 朝の商店街（買い物・すれ違い） | V01/V04 系 + 任意 |
| S2 | 昼の職場・店（同僚・常連） | 任意 |
| S3 | 夕方の公園・居酒屋（雑談） | 任意 |
| S4 | **月替わりの窓口**：町内会 → 役所窓口 → 仲介の店先 → 記者の取材（第N月の `(N-1) % 4`） | 固定会場 |

- 会場は config の `social.venues`（V01〜V08）＋ `HOME`。
- **月の初めに1回だけ「計画コール」**：各主体が `thought` と、S1〜S4 の**行き先4つ**を返す。
- 各シーンで、同じ会場を選んだ者が**同席**する。同席者が2人以上なら会話、1人以下なら何も起きない
  （その主体はそのシーンでコールされない＝独り言は月初の thought がそれにあたる）。
- 会話は **2ラウンド**（`scene_rounds`・既定2。3も設定可）。各ラウンドで同席者**全員に個別コール**し、
  返した発話をそのラウンドの終わりに**同席者全員へ全文配送**する。したがってラウンド2は
  ラウンド1の全発言を読んでから話す＝往復になっている。
- **S4 は月替わりの会場に行った者だけが参加**する（行くかどうかは計画コールで主体が選ぶ）。
  役所窓口の月に窓口へ行った者は、`registry` の兆候（その月までの名義変更履歴）を**その月の観測で**見る。
- 発話は**同席者に全文**届く。全員共通のタイムラインは無い。

### 4.1 私信・記事・月末の姿勢（追加コールを増やさない）

- **私信（direct）**：各シーンターンの出力に `direct_to` / `direct_text` を持たせる。1主体あたり
  **月2通まで**（超過は `direct_rejected` として記録＝黙って消さない）。**翌月**に宛先へ届く。
- **記事（記者のみ）**：記者の各シーンターンの出力に `publish` を持たせる（S4に行かない月も書ける）。
  **月1本まで**（超過は `article_rejected` として記録）。記事は**翌月の全主体の観測**に
  「記事」として入る（公開発話）。行政に特別な機構は無い。
- **月末の姿勢（区画を持つ主体のみ）**：`stance`（`sell` / `keep`）は**計画コールと全シーンターンの出力**に
  持たせ、**その月のその主体の最後のコールの値**をその月の姿勢として記録する（CEO調整 2026-08-27。
  S4 に行かなかった所有者の姿勢が落ちないようにするため。シーンに一度も出なかった月は計画コールの値）。
  **これは台帳を動かさない**（買い手は台本であり、姿勢は取引ではない）。誰にも伝わらない
  内心の記録として保存し、観測に使う。プロンプトでも「記録されるだけで誰にも伝わらない」と明示する。

### 4.2 設計上の緊張（隠さず記録する）

台本で取得を固定する以上、「先月 keep と書いた主体の区画が今月移る」ことが起こりうる。
これは施主の設計判断（取得はピン留め）の当然の帰結であり、**世界が主体の判断を上書きしたのではなく、
主体の判断は初めから取得の可否に接続されていない**（v5 で問うのは気づきであって取引ではない）。
売主には結果が「自分の登記事実」として渡り、それをどう受け止め誰に話すかは本人の thought が決める。
次の実験条件の候補（要施主判断）として、`台本が sell と書いた主体の中から取得先を選ぶ` 版を
6章に挙げる。**今回は実装しない**。

## 5. 主体ループ（キモ）

```
[計画コール（月1回・全主体）]
  入力 = 先月の自分の最後の thought（全文）
       ＋ 先月末に届いた私信・記事
       ＋ 今月自分に見えた兆候（registry を除く。registry は窓口に行った月のシーンで見る）
       ＋ 自分の登記事実（自分の区画・自分が売った履歴）
       ＋ 近隣の登記（隣接区画の現在の名義＝日常的に見えている範囲）
  出力 = {thought, plan_s1, plan_s2, plan_s3, plan_s4}

[シーンターン（S1..S4 × ラウンド1..2・同席者のみ）]
  入力 = 自分の最後の thought（全文）
       ＋ 今月これまでに自分が聞いた会話（全文・シーン順）
       ＋ 今いる会場と同席者の名前
       ＋ 今月自分に見えた兆候
       ＋ 自分の登記事実
  出力 = {thought, text, talk_to[], direct_to, direct_text} （+記者は publish・区画所有者は stance）
```

- **指示するのは順序だけ**（「まず内心を書き、それを踏まえて話す」）。内容・方向・話題は指示しない。
- 世界の説明は最小＝**この街／自分の区画／シーンとは何か**だけ。目的・課題・注目すべき点は書かない。
- `thought` は毎ターン更新され、**次のターン／次の月へそのまま持ち越す**（要約しない＝E1の既定条件）。
- 発話しない月・ターンは `text` を空文字にしてよい（沈黙も観測対象）。

### 5.1 出力長と max_tokens（Codex指摘の再発防止）

- `thought` 目安 **250字以内**、`text` 目安 **150字以内**、`publish` 目安 **300字以内**。
- `max_tokens = 1400`（v4.1b の 1200 から引き上げ）。
- **スモークで実測**する：出力トークンの最大値・`truncated` 件数・`parse_fail` 件数。
  truncated>0 なら本走前に max_tokens を上げる（配線の欠陥修正であり、主体の判断への介入ではない）。
- 入力長も実測してログに残す（プロンプト最大トークン）。

## 6. 観測（全部ログから事後集計・機械／`tools/run_metrics.py` の `metrics_v5`）

出力＝ `metrics_v5.json`。

1. **初認知**（取得ごと）：`first_mention` = その取得（区画IDまたは新名義）に**当事者（売主）以外**が
   初めて言及した {月, 主体, シーン, 会場}。直前に何を見聞きしていたか（その主体がその月までに
   見た兆候／聞いた発話のうち当該取得に触れるもの）を `trigger` として併記する。
2. **伝播グラフ**：取得に言及した発話ごとに `speaker → 同席者全員` の辺を張る（月・シーン・会場つき）。
   `edges.jsonl` と、主体別の初言及の系列。
3. **噂の変形**：取得に言及した発話を**事後LLM分類**で `fact` / `exaggeration` / `error` / `unclear`
   に分ける（分類器は既存 `kpi.classify_utterances` と同じ方式・走行中の主体には一切見せない）。
4. **明るみに出たか**：
   - `article_months` … 記者の記事のうち取得に言及したものの月
   - `assembly_months` … 町内会シーンで取得に言及した発話が出た月
   - `counter_months` … 役所窓口シーンで取得に言及した発話が出た月
   - いずれも**0件のまま終わった**ことを同じ重みで記録する
5. **気づかれずに終わった取得の割合**：`unnoticed_ratio` = 当事者以外の言及が最後まで0だった取得数 ÷ 総取得数
6. **元所有者の沈黙・発言**：売主ごとに `spoke_about_own_sale`（初言及の月／最後まで黙ったか）と、
   thought に自分の売却が現れた月
7. 健全性：`calls` / `errors` / `truncated` / `parse_fail` / `direct_rejected` / シーン別の同席者数分布

### 6.1 「取得への言及」の判定（走行前に固定・ルールベース＋事後LLM）

ルールベース1次抽出（機械・走行後に変えない）：発話文に次のいずれかが含まれる。
- 取得済み区画のID（`P\d+` 形式）
- 台本の名義（`A社` / `B社` / `C社` / `D社`）
- 語句：`名義` / `所有者が変わ` / `売られ` / `手放し` / `買い取` / `買われ` / `地上げ` / `底地` /
  `よそ者` / `外の会社` / `東京の会社`

1次抽出に掛かった発話だけを事後LLMに渡し、`about_acquisition`（true/false）と3.の変形分類を得る。
**metrics は LLM が true とした発話だけを数える**（1次抽出は絞り込みであって判定ではない）。

## 6.2 判定（**走行前に固定**・結果を見てから決めない）

- **D1（個別取得の露見）**：ある取得が、**当事者（売主）以外の3主体以上**の発話で言及された。
- **D2（街の露見）**：以下のいずれかが1回でも起きた ＝ ①記者の記事が取得に言及した
  ②町内会シーンで同一月に3主体以上が取得に言及した ③役所窓口シーンで取得への言及が出た。
- **D3（配線の健全性）**：`parse_fail = 0` かつ `truncated = 0` かつ 各シーンで同席2人以上のグループが
  1つ以上成立、かつ全ラウンドの発話が同席者に配送されている（テストで固定）。
- D1/D2 は**成功条件ではない**。「起きなかった」も同じ重みの結果として報告する。
  実走前に決めるのは定義であって、望ましい値ではない。

## 8. ルールベース自己点検（実装が満たすことをテストで固定する）

| 点検項目 | v5 の状態 |
|---|---|
| 確率・閾値・強制・指示文・台本が**出来事にだけ**あるか | 台本＝取得と兆候の配布のみ。主体の出力に世界が介入する箇所は無い |
| 主体の判断に世界が触れるか | 触れない。`stance` は台帳を動かさない。発話は改変されない（長さ超過も切らず全文保存） |
| 「気づかせる仕組み」があるか | 無い。兆候の量・可視範囲は台本で固定、結果を見て変えない |
| 行政・記者に特権的な観測があるか | 無い。行政は窓口で聞くだけ。記者の記事は「翌月の公開発話」であって世界の機構ではない |
| 主体に目的・課題・注目点を指示しているか | していない。プロンプトは順序（内心→発話）と場の説明だけ |
| 世界が主体の代わりに補正するか | しない。無効な会場・宛先は補正せず `invalid` として記録し、その月は何も起きない |
| 金銭 | 世界に存在しない。プロンプト・スキーマ・観測に金額語を出さない（テストで固定） |

**足してよい修正は配線の欠陥だけ**（出力打切り・ID不一致・配送漏れ）。
「この動きが出ないから世界に○○を足す」は禁止。
